# Golden Fixture Generator (`tools/generate_goldens/`)

Host-side tool that produces compilable Rust `const`-array fixture files for
hematite-nn's TDD golden-vector test corpus. These fixtures are consumed by
Phase 2 (`hematite-ref`) and Phase 5 (`hematite-tests` model zoo).

## ⚠️ PROVENANCE WARNING — READ THIS FIRST

**The golden values in `hematite-tests/goldens/*.rs` were NOT captured from an
executed TFLite Micro binary.** They were generated by a faithful scalar
reimplementation of the TFLM int8 reference kernels inside this tool.

This means:
- The emitted values are **best-effort faithful** to the TFLM arithmetic
  specification (i32 accumulate, `MultiplyByQuantizedMultiplier` with
  `SaturatingRoundingDoublingHighMul` + `RoundingDivideByPOT`, per-channel
  requantize, saturating cast, zero-point handling, fused-activation clamping).
- They have **NOT** been cross-validated against a running TFLM interpreter.
- **Any bit-exactness claim based on these fixtures would be circular and false**
  until T5.0 re-generates the corpus against real executed TFLM.

**The fixture files themselves carry this provenance note in a `GOLDEN_PROVENANCE`
const, and `tools/generate_goldens/README.md` explicitly records this as
outstanding technical debt.**

### Remediation (T5.0)

T5.0 must:
1. Build TFLite Micro at the pinned SHA `18b9e6f2a8c5a9518e588f59c2ba16ef7ef9d551`
   on the host.
2. Link a C++ harness against the TFLM interpreter that runs each op with
   the same input tensors.
3. Capture the exact `int8` outputs from the executed TFLM binary.
4. Overwrite the generated fixture files.
5. Remove the `GOLDEN_PROVENANCE` fallback const from every fixture.
6. Verify that every Hematite kernel's output is bit-exact against the new
   real-TFLM fixtures.
7. Only then may any public bit-exactness claim be made, and only then may
   Phase 5 benchmarking conclusions be drawn.

## Architecture

```
tools/generate_goldens/
├── Cargo.toml        # Standalone workspace member
├── README.md         # This file
├── zoo/
│   ├── run_model.py      # Executed-TFLite model golden harness (ai-edge-litert)
│   └── fetch_espdl.sh    # Downloads the 15 esp-dl .espdl zoo artifacts + SHA256
└── src/
    ├── main.rs       # CLI entry point, self-check assertions
    ├── tflm_math.rs  # TFLM arithmetic primitives (MultiplyByQuantizedMultiplier, etc.)
    ├── fixture.rs    # Fixture file writer (SPDX header, const arrays, provenance consts)
    └── ops/
        ├── mod.rs
        ├── conv2d.rs            # Conv2D 1×1 + 3×3
        ├── depthwise_conv2d.rs  # DepthwiseConv2D
        ├── fully_connected.rs   # FullyConnected
        ├── matmul.rs            # BatchMatMul (int8, FullyConnectedParams path)
        ├── pool.rs              # AveragePool2D, MaxPool2D
        ├── softmax.rs           # Softmax (int8 polynomial)
        ├── activations.rs       # ReLU, ReLU6, HardSwish, LeakyReLU, PReLU, Sigmoid, Tanh
        ├── elementwise.rs       # Add, Mul, Sub (requantized)
        ├── quantize.rs          # Quantize, Dequantize
        ├── data_movement.rs     # Reshape, Transpose, Concat, Split, Pad, Slice, ResizeNearest
        ├── reductions.rs        # Mean, Sum, ArgMax, ArgMin, L2Normalization, ReduceMax, ReduceMin
        ├── recurrent.rs         # LSTM, SVDF, GRU (hand-rolled gate math)
        └── zoo.rs               # Per-model goldens via executed TFLite interpreter
```

## Model goldens (T5.0) — executed TFLite cross-check path

Model-level fixtures are captured from a **real executed TFLite interpreter**
(ai-edge-litert, the successor to tflite-runtime), not the tool-internal
reimplementation:

- `src/ops/zoo.rs` scans `models/` for runnable `.tflite` files and invokes
  `zoo/run_model.py` (project venv at `zoo/.venv`, `pip install ai-edge-litert`)
  as a subprocess, then writes the captured int8 output via
  `FixtureWriter::write_model` into `hematite-tests/goldens/models/<name>.rs`.
- These fixtures carry distinct provenance:
  `GOLDEN_PROVENANCE = "captured-from-executed-TFLite-interpreter; see
  tools/generate_goldens/zoo/run_model.py"` plus `GOLDEN_RUNTIME_VERSION`.
- **The 18-model zoo is NOT runnable through this path as of T5.0.** All 15
  esp-dl artifacts are the proprietary `.espdl` format (zero `.tflite` files
  exist anywhere in esp-dl — verified across all branches/tags/history), and
  the 6 edge-ml models are not publicly available. Full accounting in
  `models/zoo/DEFERRED_MODELS.md`. The mechanism is proven end-to-end with
  `models/sine.tflite` (the workspace's only runnable TFLite model).

## TFLM Reference Pin

```
tflite-micro SHA: 18b9e6f2a8c5a9518e588f59c2ba16ef7ef9d551
Repository:       https://github.com/tensorflow/tflite-micro
```

Every generated fixture embeds this SHA in a `GOLDEN_TFLM_VERSION` const.
The generator asserts this pin at startup (T5.0 requirement B3) — if the
constant in `src/fixture.rs` ever drifts from the corpus, regeneration fails
loudly instead of silently producing a mismatched corpus.

### GRU Provenance (T3)

**TFLM has NO GRU kernel** at the pinned SHA `18b9e6f2a8c5a9518e588f59c2ba16ef7ef9d551`.
The GRU golden fixture (`gru.rs`) is generated with **hand-rolled fixed-point gate
math** using gemmlowp logistic/tanh primitives (`exp_on_negative_values` +
`one_over_one_plus_x` pipeline, same infrastructure as softmax). Verification is via
manual bit-level self-check assertions:
- `sigmoid(0) = 0.5` (Q0.11 = 1024), `tanh(0) = 0`
- Endpoint saturation (sigmoid→1.0, tanh→±1.0 for large inputs)
- Monotonicity of sigmoid response
- Update-gate behavior verified

No external reference implementation was used. The `embedded-nn` crate v0.2.1
(checked at crates.io) has NO GRU kernel — its `recurrent` module contains only
`lstm_step_s8_s16`, `lstm_step_s16`, `svdf_s8`, and `svdf_state_s16_s8`.

## How to Add an Op

Adding a new op to the generator is a small, targeted change:

1. **Create a new module** in `src/ops/` (or add a function to an existing one)
   that:
   - Defines synthetic but meaningful input/weight/bias tensors for one canonical shape
   - Runs the TFLM reference arithmetic (call functions from `tflm_math.rs`)
   - Calls `FixtureWriter::write()` or `write_simple()` to emit the `.rs` file

2. **Add an extern crate indicator**: If your module needs a new internal type,
   add it to `tflm_math.rs`, not to a separate dependency.

3. **Call the new function from `main.rs`** in the appropriate tier section.

4. **Add a self-check assertion** in `main.rs` that verifies at least one
   hand-computed value — this guards against silent arithmetic regressions.

5. **Update this README's table** with the new file.

The `FixtureWriter` handles SPDX headers, provenance consts, and formatting.
Your op module focuses purely on the arithmetic.

## Determinism

The generator is deterministic by construction (no randomness, no wall-clock
dependency). Running it twice produces byte-identical output. This is verified
in CI and confirmed after every generator change via checksum comparison.

## Naming Convention

Fixture file names use the canonical op name in lowercase with underscores
(e.g., `conv2d_1x1.rs`, `depthwise_conv2d.rs`). These are consumed by
`hematite-tests/src/goldens.rs` via `include!()` macros. The module names
within `hematite-tests` match the file names, and Phase 2 test files access
them as `hematite_tests::goldens::conv2d_1x1::INPUT_DATA`, etc.

`const` names within each fixture follow these conventions:
- `INPUT_DATA`, `WEIGHTS_DATA`, `BIAS_DATA` — input tensors
- `OUTPUT_MULTIPLIER`, `OUTPUT_SHIFT` — per-channel requantization params
- `INPUT_OFFSET`, `OUTPUT_OFFSET` — quantization zero-point offsets
- `EXPECTED_OUTPUT` — the golden reference output
- `GOLDEN_TFLM_VERSION` — the pinned TFLM SHA
- `GOLDEN_PROVENANCE` — whether these values came from real TFLM or internal reference

All Phase 2 helpers MUST follow this convention so test includes remain
consistent across the corpus.
