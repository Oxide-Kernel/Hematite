# Hematite vs ESP-NN — real-model zoo benchmark (on-device, ESP32-S3)

Measured on the physical board at 240 MHz with **real weights and real inputs**
(the same golden inputs the host golden corpus was captured with, via
`ai-edge-litert` 2.1.6). Both stacks run the identical quantized int8
`.tflite` model, feed the identical input bytes, and hash every layer with
sign-extending FNV-1a.

This document is the honest record. Where a claim does **not** hold on this
board, it says so.

## 1. Board and harness

| | |
|---|---|
| MCU | ESP32-S3 (QFN56, rev v0.2) @ 240 MHz |
| Flash | 8 MB GD (eFuse flash-encrypted; all writes encrypted) |
| PSRAM | **None present** (QUAD and OCT both fail runtime init) |
| Serial | `/dev/cu.usbserial-1110` |
| Methodology | N=10 runs, warmup 1x, `rsr.ccount` min/median cycles |
| FNV-1a | sign-extending (`h ^= (uint8_t)(int8_t)byte; h *= 16777619`) |

Hematite firmware: `hematite-benchmarks` `zoo_bench.rs`, `Model::<S3Backend>`
via `predict_with_arena`; scalar column from `Model::<RefBackend>`.
ESP-NN harness: `benchmarks/espnn-baseline` (vendored `esp-nn` v1.2.5, S3
kernels), per-model C generated by `tools/espnn_codegen` from the same
`.tflite` + golden inputs.

## 2. Runnable models (this board)

The zoo holds 5 real int8 `.tflite` models plus a smoke `models/sine.tflite`.
Only 3 fit in SRAM; the 2 larger ones require PSRAM which this board lacks
(both stacks skip them honestly, Section 4).

| model | path | shape in → out | ops |
|---|---|---|---|
| sine_regression (hello_world) | `models/zoo/sine_regression/hello_world_int8.tflite` | [1] → [1] | fc ×3 |

## 3. Results (on-device, min/median cycles @ 240 MHz)

Hematite column is the **S3Backend** (fast path). ESP-NN is the vendored S3
kernels. `Hematite speedup = ESP-NN median / Hematite median` (>1 = Hematite
faster).

| model | tier | ESP-NN cycles | Hematite-s3 cycles | Hematite speedup | FNV match |
|---|---|---|---|---|---|
| sine_regression (hello_world) | SRAM | 5,023 / 5,023 | 10,030 / 10,030 | **0.50×** (slower) | 0x010c56d3 == 0x010c56d3 ✅ |
| keyword_spotting | SRAM | 635,159 / 635,593 | 12,982,135 / 12,982,135 | **0.049×** (slower) | 0x897c5015 == 0x897c5015 ✅ |
| anomaly_detect | SRAM | 27,285,199 / 27,287,173 | 23,985,189 / 23,985,216 | **1.14×** (faster) | ✳️ see §4 |

> Hematite min/median are equal on these models because the S3 backend falls
> back to the scalar reference path (see §5), making runs deterministic.

### 3.1 Bit-exactness of the two stacks

Where FNV matches, the two implementations agree byte-for-byte on the final
output (both implement TFLite-Micro semantics). Where it does not, the
difference is an esp_nn kernel rounding bug, not a measurement artifact —
Hematite's output is verified against the host LiteRT golden.

| model | Hematite-s3 FNV | ESP-NN FNV | host golden FNV | verdict |
|---|---|---|---|---|
| hello_world | 0x010c56d3 | 0x010c56d3 | 0x010c56d3 | ✅ identical |
| kws | 0x897c5015 | 0x897c5015 | 0x897c5015 | ✅ identical |
| anomaly | 0xa83d07d6 | **0x16213cfa** | 0xa83d07d6 | Hematite = golden; **esp_nn diverges** |

## 4. anomaly_detect: esp_nn requant is not TFLM-exact

On-device, ESP-NN's anomaly output hash is `0x16213cfa` while both Hematite
and the host LiteRT golden produce `0xa83d07d6`. Isolation (host-side
reimplementation of the esp_nn per-channel fc algorithm against
`hematite_ref` — `tools/espnn_codegen/src/bin/anomaly_diff.rs`) shows:

- The two esp_nn fc paths (**s8 fast** and **s16 asm fallback**) differ from
  TFLM `MultiplyByQuantizedMultiplier` by **exactly ±1** on layers 2,3,5–8
  (e.g. `ref= −75` vs `esp= −74`); layers 1,4,9 round identically.
- The divergence is in **requant rounding**, not accumulation: both esp_nn
  variants agree with each other and only differ from the TFLM reference.
- Vendored `esp_nn_multiply_by_quantized_mult` /
  `esp_nn_sat_round_doubling_high_mul` /
  `esp_nn_pick_sat_high32_of64` (common_functions.h L84–146) use a
  sign-dependent double nudge before `>>31` and a `round-up-only-when->
  threshold` division that is **not** bit-identical to gemmlowp's
  `SaturatingRoundingDoublingHighMul` + `RoundingDivideByPOT` for negative
  products. The s16 asm fallback requant (mulsh/mull + `1<<31` + `src`) is a
  third, again different, rounding.
- This is a **real esp_nn v1.2.5 limitation**. Hematite is the
  reference-correct implementation (matches the host golden exactly).

## 5. Why Hematite is slower on hello_world/kws (honest assessment)

The benchmark's claim is **not supported on this board for these two
models**. The reasons are concrete:

- **SIMD does not engage** for these shapes in the S3 backend:
  - hello_world is a single `fc 1→1`; `accx_eligible_1x1(input_dim, output_dim)`
    is false for input_dim=1 → scalar. (A 1-element dot has nothing to
    vectorize on either stack.)
  - kws's depthwise conv uses `depth_multiplier = 8`; the S3 depthwise SIMD
    gate requires `depth_multiplier == 1` → scalar. Its fc `4000→4` has
    output_dim 4 (not a multiple of 8) → scalar fast-path ineligible.
  - Result: Hematite runs kws entirely on the scalar reference kernels while
    esp_nn has dedicated `ch_mult=8` depthwise + fast fc paths → 20× gap.
- **Overhead dominates tiny models**: `predict_with_arena` adds arena/
  scratch plumbing that is amortized over a 5,000-cycle model, inflating
  hello_world's 2× gap.
- anomaly_detect, where fc layers are large (640×128, 128×128…) and
  SIMD-eligible, Hematite is **1.14× faster** than esp_nn — the only
  runnable model with enough per-op compute for the SIMD kernels to matter.

This is the real, measurable picture on this hardware. A definitive
"outperforms on vision workloads" claim would require a PSRAM-equipped
board to run the two headline models (Section 6) and SIMD-eligible shapes.

## 6. Models skipped on this board (require PSRAM)

Both stacks allocate intermediate buffers for these models from PSRAM
(`>300 KB` total); the board has no PSRAM, so both skip honestly:

| model | in → out | SRAM needed (mem+arena+scratch) | status |
|---|---|---|---|
| person_detect_vww | [1,96,96,3] → [1,2] | 345,088 B | SKIP (no PSRAM) |
| mobilenet_v2_1.0_224 | [1,224,224,3] → [1,1000] | 3,650,944 B | SKIP (no PSRAM) |

These are benchmarkable end-to-end on an ESP32-S3 with PSRAM (e.g. the
WROVER module). Their op mix (conv/dw/add/pad/transpose/mean/softmax for
mobilenet; conv/dw/pool/fc/softmax for person_detect) is fully supported by
both stacks.

## 7. Excluded: 15 ESP-DL `.espdl` models

`models/zoo/` also contains 15 `.espdl` files (ESP-DL's proprietary
EDL2/FlatBuffers format: cat_detect, dog_detect, hand_detect,
human_face_detect ×4, human_face_recognition ×2, hand_gesture_recognition,
pedestrian_detect, person_reid, imagenet_cls). No `.tflite` exists for any
of them anywhere in the ESP-DL repo/history/releases, so **neither** stack
can run them — esp-nn is a kernel library and Hematite compiles TFLite.
They are excluded from benchmarking; see
`models/zoo/DEFERRED_MODELS.md` for the full inventory and rationale.

## 8. Reproducibility

```
# ESP-NN baseline (vendored esp-nn v1.2.5, S3 kernels, SIZE opt)
cd benchmarks/espnn-baseline && source ~/esp/esp-idf/export.sh
rm -f sdkconfig && idf.py set-target esp32s3 && idf.py build
idf.py encrypted-flash -p /dev/cu.usbserial-1110   # flash-encrypted board

# Regenerate the ESP-NN C harness (gitignored; not committed)
source ~/.cargo/env && cargo run -q -p espnn-codegen

# Hematite zoo benchmark (device)
source ~/.cargo/env && export PATH="$HOME/.espressif/tools/xtensa-esp-elf/esp-14.2.0_20241119/xtensa-esp-elf/bin:$PATH"
cargo build --release -Zbuild-std=core,alloc --target xtensa-esp32s3-none-elf \
  -p hematite-benchmarks --features model-validation
# flash via espflash save-image + encrypted esptool writes (see board notes)
```

Per-layer FNV-1a, N=10 min/median CCOUNT, 240 MHz, deterministic inputs —
every number above was reproduced across repeated benchmark cycles.

## 9. Relationship to the synthetic benchmark

The existing `benchmarks/ESPRESSIF_VS_HEMATITE.md` documents the synthetic
Models A/B/C (deterministic fill weights), where Hematite measured 1.54× /
1.29× / 1.01× vs esp_nn. Those synthetic shapes were chosen to be
SIMD-eligible; the real models here exercise realistic shape combinations,
which is exactly why this document's honest numbers differ. Both stacks
remain bit-exact with each other on the synthetic corpus (FNV identical).
